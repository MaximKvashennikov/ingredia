# User administration

## Purpose

Веб-админка MVP для просмотра учётных записей и управления доступом пользователей ingredia с проверяемыми правами и аудитом.

## ADDED Requirements

### Requirement: Authorized administrator access

Система SHALL разрешать управление пользователями только активному аутентифицированному администратору и проверять право на каждом запросе. Скрытие UI SHALL не заменять серверную проверку; роль оператора подключений SHALL сама по себе не давать административных прав.

#### Scenario: Regular user calls the administrative API
- **WHEN** обычный пользователь или оператор без административного права обращается к списку пользователей либо изменению статуса
- **THEN** сервер отклоняет запрос без раскрытия списка и изменения учётных записей.

#### Scenario: Client supplies an administrator role
- **WHEN** клиент передаёт административную роль в регистрации, профиле или параметрах запроса
- **THEN** система не выдаёт административное право из этих данных.

### Requirement: Searchable user directory

Система SHALL предоставлять администратору постраничный список, поиск по внутреннему ID или отображаемому имени, фильтр статуса и карточку аккаунта: ID, имя, дата регистрации, статус, роль и наличие привязанных каналов. Это право SHALL не открывать содержимое холодильника, избранного, фото и голосовых пользователя.

#### Scenario: Search accounts with identical names
- **WHEN** администратор ищет имя, принадлежащее нескольким аккаунтам
- **THEN** он видит различимые по внутреннему ID записи и может открыть нужную карточку без смешивания аккаунтов.

#### Scenario: No matching users
- **WHEN** поиск или фильтр не находит пользователей
- **THEN** интерфейс показывает пустой результат и возможность изменить запрос, сохраняя текущие фильтры.

#### Scenario: Administrative permission does not grant content access
- **WHEN** администратор пытается прочитать личный рецепт или холодильник другого пользователя, имея только право управления аккаунтами
- **THEN** сервер отклоняет доступ к содержимому.

### Requirement: Confirmed account status management

Система SHALL позволять администратору блокировать и разблокировать обычный аккаунт после подтверждения с указанием причины. Операции SHALL сохранять личные данные, проверять версию записи и применяться идемпотентно. Админка MVP SHALL не позволять заблокировать свой или другой административный аккаунт.

#### Scenario: Block an ordinary account
- **WHEN** администратор подтверждает блокировку выбранного обычного аккаунта и указывает причину
- **THEN** статус становится blocked, личные данные сохраняются, а интерфейс показывает актуальный результат.

#### Scenario: Cancel status change
- **WHEN** администратор отменяет подтверждение блокировки или разблокировки
- **THEN** статус аккаунта не меняется.

#### Scenario: Repeated or stale status request
- **WHEN** повторяется прежняя операция с тем же ключом либо запрос опирается на уже изменённую версию аккаунта
- **THEN** повтор возвращает прежний результат без нового изменения, а устаревшая независимая операция сообщает конфликт и требует повторного подтверждения.

#### Scenario: Protect an administrator account
- **WHEN** администратор пытается заблокировать свой или другой административный аккаунт
- **THEN** сервер отклоняет операцию и сохраняет административный доступ.

### Requirement: Blocked access across clients and jobs

Система SHALL после блокировки отклонять защищённые действия аккаунта в вебе и Telegram, включая действия со старой сессией и применение ожидающих заданий. Проверка статуса SHALL согласовываться с записью изменений. Разблокировка SHALL не запускать автоматически отменённые действия.

#### Scenario: Previously authenticated blocked user
- **WHEN** заблокированный пользователь со старой веб-сессией или Telegram-кнопкой пытается изменить запас, сохранить рецепт либо открыть личные данные
- **THEN** действие отклоняется с безопасным сообщением о блокировке.

#### Scenario: AI task finishes after blocking
- **WHEN** аккаунт заблокирован до применения результата ранее начатого распознавания
- **THEN** результат не изменяет запасы и не выдаётся как успешно добавленная покупка; задание получает явный отменённый по блокировке исход.

#### Scenario: Unblock an account
- **WHEN** администратор подтверждает разблокировку
- **THEN** аккаунт снова может пройти проверку доступа и пользоваться сохранёнными данными, но отменённые задания не исполняются автоматически.

### Requirement: Account administration audit

Система SHALL записывать административные изменения статуса и отказы доступа с субъектом, целевым ID, действием, временем, причиной, результатом и correlation ID без секретов и личного содержимого. Изменение статуса SHALL фиксироваться согласованно с записью аудита; журнал SHALL быть доступен только уполномоченному администратору.

#### Scenario: View status history
- **WHEN** администратор открывает историю управления выбранным аккаунтом
- **THEN** он видит авторов, причины и результаты административных действий без фотографий, голосовых, токенов и рецептов.

#### Scenario: Audit persistence fails
- **WHEN** при изменении статуса невозможно сохранить связанную запись аудита
- **THEN** изменение не фиксируется, а интерфейс сообщает об ошибке без ложного подтверждения успеха.

### Requirement: Usable administrative interface

Система SHALL предоставлять веб-интерфейс управления пользователями с состояниями загрузки, пустого списка, ошибки, подтверждения и результата. Элементы управления SHALL иметь понятные подписи и доступ с клавиатуры; ошибка SHALL сохранять поисковый запрос и фильтры без заявления об успешном изменении.

#### Scenario: Status update fails
- **WHEN** сервер не подтверждает изменение статуса
- **THEN** интерфейс показывает ошибку либо неизвестный исход с возможностью обновить карточку и не изображает неподтверждённый статус как сохранённый.

#### Scenario: Keyboard navigation
- **WHEN** администратор работает только клавиатурой
- **THEN** доступны поиск, карточка, подтверждение и отмена; фокус видим, а результат изменения объявляется вспомогательной технологии.
