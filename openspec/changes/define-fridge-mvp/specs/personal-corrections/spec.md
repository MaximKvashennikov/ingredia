# Personal corrections

## Purpose

Использовать исправления конкретного пользователя для более подходящих будущих предложений, сохраняя
возможность объяснения и сброса.

## ADDED Requirements

### Requirement: Scoped correction memory

Система SHALL запоминать пользовательские исправления распознавания, единиц, типовой упаковки и
оценочного срока в контексте продукта и условий. Правила SHALL принадлежать только этому
пользователю и не изменять данные других пользователей.

#### Scenario: Familiar product name
- **WHEN** пользователь исправил распознанное название своей типовой покупки и похожий ввод
  повторяется
- **THEN** система учитывает его исправление как персональную подсказку и сохраняет возможность
  уточнения при неоднозначности.

#### Scenario: Another user
- **WHEN** другой пользователь отправляет похожую покупку
- **THEN** персональные исправления первого пользователя не раскрываются и не применяются.

### Requirement: Estimates never override direct evidence

Система SHALL использовать персональные поправки к срокам только для оценок с совместимыми
условиями. Явная маркировка или текущий ввод пользователя SHALL иметь приоритет над ранее выученной
оценкой.

#### Scenario: Earlier average conflicts with packaging
- **WHEN** ранее пользователь обычно выбирал более длинный срок, но на новой упаковке указан более
  ранний
- **THEN** система сохраняет срок упаковки и не продлевает его персональным правилом.

#### Scenario: Storage conditions changed
- **WHEN** поправка относилась к закрытой упаковке, а текущий продукт вскрыт
- **THEN** система не переносит срок автоматически без правила для соответствующих условий.

### Requirement: Explainable personalization

Система SHALL обозначать применение персональной поправки и позволять увидеть её происхождение.
Персональная оценка срока SHALL оставаться оценкой, а не доказанным сроком безопасности.

#### Scenario: Personalized expiry suggested
- **WHEN** новая оценка учитывает прошлое исправление пользователя
- **THEN** система помечает её «по вашим исправлениям» и позволяет изменить результат.

### Requirement: Reset without rewriting history

Система SHALL позволять отключить применение или удалить персональные правила. Сброс SHALL влиять на
будущие предложения, сохраняя явные текущие записи продуктов до отдельного редактирования.

#### Scenario: User resets learned corrections
- **WHEN** пользователь сбрасывает персональные поправки
- **THEN** последующие предложения не используют их, а ранее сохранённые партии не пересчитываются
  молча.

### Requirement: Separate correction from recurring rule

Система SHALL различать исправление одной партии и основание для будущих предложений. Одиночная
корректировка даты SHALL не считаться универсальным подтверждением срока для всех партий продукта.

#### Scenario: One package is unusual
- **WHEN** пользователь меняет дату только одной упаковки
- **THEN** система обновляет её запись; при использовании изменения в будущем показывает его как
  предположение, а не обязательное правило.
