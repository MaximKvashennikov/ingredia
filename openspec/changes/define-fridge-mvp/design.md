# Design

## Context

Пользователь описал два сценария: фотография видимых продуктов для выбора блюда и добавление покупок фотографией или голосом. Текущий канал — Telegram; ВК только предполагается на будущее. Общая инфраструктурная основа описана в [соседнем change](../establish-platform-foundation/design.md).

Стек: FastAPI, React/TypeScript, PostgreSQL, uv, QA только pytest. Android планируется в будущем через общий API; разработка мобильного клиента сейчас исключена. Этот документ описывает будущую реализацию; код, зависимости и внешние сервисы сейчас не создаются.

## Goals / Non-Goals

**Goals:** провести оба сценария через общее ядро, сохранить достоверность запасов при неоднозначном вводе, обеспечить объяснимые оценки и расширяемость каналов.

**Non-Goals:** реализация ВК, семейный доступ, заказы продуктов, медицинские рекомендации, автоматическое обучение общей модели, гарантии свежести по фото, автоматическое списание продуктов при чтении рецепта.

## Decisions

### 1. Ports and adapters в модульном монолите

Внутреннее ядро содержит сущности и правила запасов, диалоговых сессий, подбора рецептов и персональных исправлений. Прикладной слой координирует сценарии. Адаптеры переводят внешние протоколы в типизированные команды и результаты ядра. Сборка приложения внедряет зависимости; ядро не выбирает SDK через условие `if telegram`.

| Граница | Ответственность порта | Адаптер MVP | Возможное расширение |
| --- | --- | --- | --- |
| Входной канал | Нормализованные события, идентичность, вложения и действия | Telegram | ВК, только после отдельного запроса |
| Выходной канал | Текст, карточки, кнопки, ошибки и progress | Telegram renderer/sender | Другие представления без переписывания use cases |
| Vision | Кандидаты продуктов, OCR-атрибуты, неопределённость | Выбранный впоследствии AI-поставщик | Замена поставщика |
| Speech-to-text | Транскрипция, неоднозначные участки, ошибка | Выбранный впоследствии STT-поставщик | Другая модель |
| Recipe provider | Кандидат рецепта и происхождение | Каталог или генератор, выбор до реализации | Несколько источников |
| Shelf-life source | Средняя длительность, условия и источник | Версионируемый справочник | Новый справочник с миграцией версии |
| Persistence / jobs | Транзакции, репозитории, outbox, задачи | PostgreSQL; worker-процесс того же приложения | Замена механизма доставки задач без утечки SDK в домен |

Голосовое сообщение само по себе запускает сценарий добавления покупок: Telegram voice → проверка и ограниченная загрузка аудио → speech-to-text с отметкой неясных участков → извлечение продуктов, количества, объёма и явно названных сроков из транскрипта → проверка кандидатов, адресное уточнение и запись однозначных позиций. Извлечение атрибутов может использовать общий LLM-порт или специализированный парсер; ни STT, ни LLM не записывают запасы напрямую.

В фазах 0–1 для речи сравнить готовый внешний STT, готовую модель при локальном размещении и собственную адаптацию/обучение. Собственный вариант не обязателен: его выбирать только после оценки качества на русских продуктовых названиях, числах, единицах, шуме и коротких сообщениях, с учётом разрешённых данных для обучения, лицензии, стоимости вычислений и сопровождения. При недоступности или неуверенной транскрипции сохранять безопасный путь уточнения или текстового ввода без выдуманных покупок.

FastAPI и Telegram являются входами в одни прикладные операции, а не двумя реализациями бизнес-логики. React обращается к HTTP API и не обращается к AI или Telegram напрямую. Реестр доверенных адаптеров и dependency injection достаточны: динамическая загрузка плагинов, service mesh и отдельные микросервисы не нужны для этих двух сценариев.

Будущий Android также обращается к версионируемому HTTP API и использует тот же User ID/холодильник. Данные ответов структурированы: мобильному клиенту не нужно разбирать сообщения Telegram. Вход, медиа-загрузка и асинхронные результаты отделены от протокола бота. Мобильный UI, офлайн-синхронизация и push потребуют отдельного будущего change.

Контракт входного события: channel, installation ID, external event ID, external sender ID, conversation ID, reply/action reference, timestamp и типизированное содержимое. Дедупликация учитывает канал и установку бота. Идентичность пользователя определяется сервером после проверки транспорта, а не из AI-ответа или поля запроса клиента.

Контракт результата содержит предметные данные и семантические действия: уточнить позицию, открыть рецепт, сохранить рецепт, отменить конкретное добавление. Telegram-адаптер переводит их в текст/кнопки, учитывая лимиты. Слишком длинный ответ делится адаптером; use case не знает о количестве символов Telegram.

### 2. Разделение сценариев и состояние диалога

Режим выбирается кнопками «Что приготовить» / «Добавить покупки» или однозначным текстом, включая транскрипцию голосового. Ясное «купил...» может сразу открыть добавление покупок без кнопки; при неопределённости вопрос задаётся до изменения запасов. Намерение сохраняется в IntakeSession, привязанной к пользователю, диалогу и сообщению.

Предлагаемые состояния сессии: received → processing → needs_clarification / partially_applied / completed; отдельно failed и cancelled. Каждая позиция имеет собственный статус, чтобы уточнение четвёртого продукта не добавляло первые три повторно.

Покупки: получение медиа → распознавание → нормализация → проверка → добавление однозначных позиций → сводка и вопросы по оставшимся. Продукт с неизвестным объёмом можно сохранить с неизвестным атрибутом; неясная идентичность продукта требует ответа. Пользователь не подтверждает повторно каждую очевидную позицию.

Рецепты: получение фото → распознавание → уточнение → сопоставление с холодильником → подбор → карточки и избранное. Подбор и просмотр сами по себе не пополняют и не списывают запасы, не удаляют невидимые продукты. «Добавить отсутствующий продукт» и подтверждённое «Закончилось» запускают отдельные явные операции; «Не использовать сейчас» меняет только текущий подбор.

Вопрос содержит ссылку на конкретную позицию; ответы проверяют пользователя, сессию и её версию. Новое сообщение не должно случайно отвечать на старый вопрос. При истёкшей/отменённой сессии бот предлагает актуальное действие.

### 3. Модель запасов и происхождение атрибутов

| Сущность | Значимые поля | Инварианты |
| --- | --- | --- |
| User / ChannelIdentity | Internal user ID, display name, created_at, status, version, roles; channel, external sender ID | Внешнее имя не является идентификатором; личные данные изолированы; blocked запрещает защищённые действия |
| Product | Canonical ID/name, category, aliases | Нормализация названий не объединяет партии |
| InventoryBatch | Owner, product, count, per-package amount/unit, remaining amount/unit, added/opened dates, storage conditions, version | Остаток неотрицателен; неизвестные числа допустимы |
| AttributeEvidence | Field, value, source, estimated flag, confidence/reason, reference | Различаются слова пользователя, OCR, модель, справочник и персональная оценка |
| ExpiryEstimate | Date, date precision, source, anchor, storage assumptions, rule/catalog version | Оценка не превращается в маркировку; дата покупки не считается датой производства |
| IntakeSession / Item | Owner, intent, source event, candidates, item status, applied operation ID, version | Один item применяется один раз; вопросы адресные |
| StockOperation | ID, item/batch, delta, original version, idempotency key | Отмена — компенсирующее изменение с проверкой версии |
| RecipeSnapshot / Favorite | Stable recipe ID/version, servings, ingredients, steps, provenance; owner + recipe version | Избранное сохраняет рецепт, а не только временный AI-ответ |
| CorrectionExample / Rule | Owner, product/context, corrected field, scope, evidence, enabled/version | Персональные поправки не становятся общими правилами |

Числа хранятся без двоичных ошибок округления в количествах. Штуки, масса и объём — отдельные размерности. «2 × 1 л» означает два пакета с общим объёмом 2 л, а не дополнительную третью запись количества. Пересчёт литров в килограммы не допускается без предметных данных.

В PostgreSQL это реляционные таблицы с внешними ключами, CHECK/UNIQUE-ограничениями, числовыми значениями точной десятичной арифметики и версией записи. Срок продукта хранится как календарная дата с явно заданной точностью, момент события — как timestamp с временной зоной. JSONB подходит для ограниченных дополнительных атрибутов и нормализованных AI-результатов, но права, остатки и даты не прячутся в произвольный JSON. Полнотекстовый/семантический поиск и vector-расширения не добавляются без измеренной потребности.

PostgreSQL содержит записи outbox и задач; для MVP предлагается worker с арендой задач из БД, без обязательного Redis/RabbitMQ. Внешние вызовы не удерживают открытую транзакцию на всё время работы AI: состояния и аренда фиксируются короткими транзакциями. Отдельный брокер возможен при подтверждённой нагрузке. Медиа — во временном файловом/объектном хранилище; БД содержит ссылки, владельца и срок очистки.

Партии с разными датами, условиями или неизвестным происхождением не сливаются автоматически. Поиск рецепта может агрегировать совместимые доступные количества, сохраняя сведения о партиях и неопределённости.

### 4. Сроки и персональные исправления

Приоритет данных: текущий явный ввод пользователя о конкретной партии → однозначная маркировка → применимая персональная оценка → применимая справочная оценка → неизвестно. Исправление пользователем маркировки сохраняется как пользовательский ввод с историей, а не переписывает источник на «упаковка».

Для средней длительности необходимы категория, условия хранения и дата отсчёта. Если используется дата добавления как приближение даты покупки, это явно показывается. При неизвестной дате производства нельзя вычислять точный срок от неё. Вскрытие упаковки меняет контекст и может потребовать новой оценки.

Конкретные числа сроков не придумываются в этом пакете: нужен выбранный справочник с происхождением данных и областью применимости. Если оснований нет, система спрашивает или оставляет срок неизвестным.

Первая версия «обучения» — поиск похожих персональных исправлений и типизированные правила, а не обновление весов модели. Совпадение контекста, версия и объяснение доступны. Одиночное исправление — пример для предположения; для устойчивого предпочтения требуется подтверждённый повторяющийся контекст либо явное действие пользователя «использовать обычно». Сброс отключает будущее использование, не пересчитывает существующие партии.

Глобальное обучение на фотографиях и голосе не выполняется по умолчанию. Справочные и персональные сроки остаются оценками и не подтверждают безопасность продукта.

### 5. Подбор и избранное

Сопоставление использует нормализованный продукт и признаки; несколько подходящих партий не требуют выдумывать, какая именно упаковка на фото. Если это важно для остатка или срока, задаётся уточнение. Фото — частичное наблюдение: отсутствие продукта в кадре ничего не говорит о его отсутствии в холодильнике.

В подбор передаётся снимок подтверждённых ингредиентов, доступных запасов и неопределённостей. Основной приоритет — продукты с фото; остальные запасы могут дополнять блюдо. Генератор не объявляет отсутствующий ингредиент доступным. Любые базовые ингредиенты, замены и требуемые количества показываются явно.

Результат проверяется по схеме и сопоставляется с запасами после генерации. Классы доступности: есть достаточно; есть, количество неизвестно; подтверждено на фото, ещё не учтено; отсутствует; исключено из доступных по сроку. При просмотре сохранённого рецепта доступность вычисляется заново, а сам рецепт не генерируется повторно.

Запасы не списываются от факта просмотра. Списание по приготовлению и масштабирование порций с автоматическим резервированием могут стать отдельной фичей.

### 5.1. Коррекция из рецепта и исключение на один подбор

Пользователь согласовал две идеи из [discovery](../../../docs/product-discovery-2026-10-29.md): исправление устаревших запасов при выборе блюда и объяснимый приоритет близкого срока. Они входят в фазу 3 текущего change.

Действие «Закончилось» открывает подтверждение с выбранными партиями и прежним/новым остатком. При нескольких партиях пользователь выбирает затронутые; остальные сохраняются. Неоднозначное «молока нет» сначала предлагает два действия: исправить запасы или временно исключить продукт. Невидимость продукта на фото не вызывает коррекцию.

Подтверждённая коррекция — отдельная типизированная StockOperation с проверкой владельца, версии и идемпотентности. Отмена выполняет компенсирующую операцию и восстанавливает прежний остаток только при отсутствии последующих изменений; иначе показывается конфликт. Коррекция не является обучением персонального правила. После неё и после успешной отмены доступность и подбор пересчитываются. Сбой подбора не откатывает уже подтверждённый остаток: пользователь видит сохранённую коррекцию, неактуальность старого списка и возможность повторить только подбор.

«Не использовать сейчас» исключает из текущих рекомендаций рецепты, требующие выбранный нормализованный продукт, включая его подтверждение на фото, без изменения партий. Исключения привязаны к владельцу и сессии подбора, видимы и снимаются пользователем. Они не записываются как постоянные предпочтения и не переносятся в новый независимый подбор.

Порядок рецептов сначала учитывает соответствие запросу/подтверждённым продуктам фото и доступность ингредиентов. При прочих равных ближняя неистёкшая подтверждённая дата повышает приоритет; причина содержит продукт, дату и источник. Оценочные даты отображаются отдельно и не подменяют подтверждённую срочность; неизвестные даты не дают приоритета. Истёкшие партии исключаются по действующему правилу recipe-discovery. Числовое окно «скоро» и дополнительные веса ранжирования уточняются перед реализацией; сценарии сравнения более ранних подтверждённых дат проверяются независимо от них. Проактивные Telegram-напоминания не входят в эти две возможности.

В Telegram и React доступны одинаковые предметные действия. UX включает подтверждение, отмену подтверждения, загрузку пересчёта, успех, конфликт версии, сбой подбора и отмену сохранённого изменения. Подписи прямо сообщают, меняется ли запас; состояния и результаты доступны с клавиатуры и вспомогательных технологий в вебе. Приёмка — pytest для серверных правил и ручные UX-сценарии без скриншотного тестирования.

### 6. Безопасность, приватность и надёжность

Общие требования безопасности и устойчивой доставки берутся из foundation. Дополнительно:

- Все stock/favorite/correction операции получают пользователя из проверенного контекста. AI выдаёт только данные-кандидаты, а изменения выполняют типизированные серверные команды после проверки.
- Prompt injection из упаковки, транскрипции или ответа модели не может расширить набор операций. Модель не получает секреты бота, произвольный SQL или сетевые инструменты для выполнения команд.
- Для веб-привязки предлагается одноразовая ограниченная по времени операция подтверждения в личном Telegram-диалоге; нельзя привязывать по введённому username. Точный механизм входа оформляется перед реализацией доступа. Связывание с ВК отложено.
- Фото и голос скачиваются только через доверенный Telegram-адаптер. Проверяются фактический тип, размер, декодирование и лимит длительности; EXIF и лишние метаданные не передаются далее без необходимости.
- Предлагаемые стартовые ограничения приложения: до 10 MiB на медиа, голос до 120 секунд, временные копии не дольше 24 часов после завершения или сбоя. Это проектные значения для обсуждения, а не утверждение о лимитах Telegram. До реализации проверить совместимость выбранных API и стоимость обработки.
- TTL-очистка включает успешные, ошибочные и прерванные задания; логируется результат удаления без содержимого файла. Политика внешнего AI-поставщика проверяется отдельно: локальное удаление не означает удаление на стороне поставщика.
- Транзакция записи партии, результата item, операции и outbox предотвращает повторное добавление при потере ответа. Повтор отправки сводки не выполняет операцию stock заново.
- Для внешних AI-вызовов используются timeout, ограниченный retry для безопасных запросов, лимит параллельности и квоты по пользователю. Сбой не превращается в выдуманные ингредиенты или частично скрытый успех.

Детали Telegram берутся из официальной [Bot API](https://core.telegram.org/bots/api): преобразование photo/voice, загрузка через getFile, идентификаторы обновлений и webhook secret. Токен может присутствовать в URL Telegram API и загрузки файлов; такие URL должны удаляться/маскироваться в логах HTTP-клиента. Конкретные настройки и лимиты фиксируются в provider change перед реализацией.

### 7. UX

В Telegram основные действия: «Что приготовить», «Добавить покупки», «Мой холодильник», «Избранное». Веб: холодильник, карточка партии, рецепт, избранное и управление персональными поправками. Эти экраны — предложенный минимальный набор на заданном стеке.

После добавления сводка разделяет «добавлено», «нужно уточнить», «не распознано» и даёт действие исправления/отмены конкретного ввода. Оценки объёма и срока обозначаются рядом со значением. Вопросы короткие, по конкретной позиции, с возможностью ответить текстом.

Карточка рецепта не скрывает недостающие ингредиенты за кнопкой приготовления. Пустое избранное и пустой холодильник объясняют следующий шаг. Состояния загрузки, ошибки, повтора и частичного успеха различаются текстом. Веб наследует требования клавиатуры, фокуса и адаптивности из foundation; скриншотных тестов нет.

### 8. QA и связь со спецификациями

| Спецификация | Автоматизация только pytest | Ручная приёмка |

Тесты опираются на фиксированные ожидаемые результаты и искусственные ответы поставщиков. Качество реального vision/STT/рецептов измеряется отдельно на согласованном наборе разрешённых примеров; pytest может запускать такую оценку с явной конфигурацией. Метрики: правильность идентификации, извлечение единиц/дат, доля нужных уточнений и соответствие ингредиентов. Порог приёмки задаётся до реализации выбранного поставщика, а не объявляется достигнутым без измерений.

Тесты реальных моделей не входят в каждый обычный запуск: они могут требовать сети или значительных локальных ресурсов и быть недетерминированными даже при бесплатном доступе. Browser runners и скриншотные сравнения не вводятся. Сборка/typecheck React проверяют компиляцию, ручные сценарии — взаимодействие. ВК проверяется только как возможность контрактного расширения через fake adapter; реальных вызовов ВК нет.

### 9. Админка управления пользователями в MVP

Подтверждённый пользователем объём — веб-админка управления пользователями. Для MVP предлагаются постраничный список, поиск по ID/имени, фильтр active/blocked, карточка аккаунта, блокировка/разблокировка обычного пользователя и история административных действий. Создание аккаунтов остаётся частью выбранного входа; редактирование чужих продуктов, массовые рассылки, удаление данных и управление административными ролями через UI не добавляются этим требованием.

В User добавляются status, created_at и version, а полномочия выдаются доверенным серверным механизмом. Отдельное право управления пользователями не наследуется из роли оператора подключений и не даёт доступа к чужому холодильнику/избранному/медиа. Начальный администратор назначается документированной доверенной процедурой развёртывания после выбора аутентификации; регистрация и редактирование профиля не принимают административные полномочия из клиента. Админка MVP блокирует только обычные аккаунты: свой и другие административные аккаунты защищены серверной проверкой.

React вызывает административные операции того же версионируемого FastAPI API. Карточка содержит минимальные метаданные аккаунта, роли и наличие привязок, не содержимое личных данных. Результат поиска сохраняет фильтры при ошибке. Изменение статуса требует подтверждения и причины, версии цели и ключа идемпотентности. Журнал административных действий расширяет общие правила аудита foundation: запись actor/target/action/reason/result согласуется транзакционно с изменением статуса, без тел сообщений и секретов.

Проверка active применяется при каждом защищённом запросе веба и Telegram независимо от существующей сессии. Worker проверяет статус перед внешним вызовом и повторно перед применением результата; транзакции изменения личных данных сериализуются с изменением статуса аккаунта. Блокировка, зафиксированная первой, запрещает последующее применение результата, не откатывая уже завершённые до неё операции. Ожидающие задания отменяются по блокировке, исходящие сообщения перед отправкой перепроверяют доступ; уже начатую внешнюю отправку нельзя гарантированно отозвать. Разблокировка не повторяет отменённые операции автоматически.

QA: pytest для прав всех административных маршрутов, подмены роли, минимизации данных, подтверждения/идемпотентности/версий, атомарности аудита и гонки блокировки с worker; ручная проверка React для списка, фильтров, клавиатуры, подтверждения, отказа и неизвестного исхода. Реализация админки входит в фазу 5; базовые роли/статус и выбор административного входа — в фазу 1.

## Risks / Trade-offs

- Фото не гарантирует точность идентичности, веса и свежести → кандидатные данные, неизвестные значения, адресные уточнения и происхождение атрибутов.
- Средний срок может не соответствовать конкретной партии → явная оценка, условия и приоритет маркировки; без обещаний безопасности.
- Простые персональные правила менее гибки, чем обучение модели → зато они объяснимы, изолированы и удаляемы; сначала измеряется их эффект.
- Асинхронные сообщения могут повторяться и приходить поздно → версии сессий, item-level идемпотентность и транзакционный outbox.
- Единственный реальный канал может скрыть утечку Telegram-типов в ядро → общий contract-набор с fake adapter и проверка границ импортов при ревью.

## Migration Plan

Существующих данных нет. Реализовывать по фазам roadmap только после отдельного запроса. Версионировать схемы событий, данные партий и персональные правила. На первом запуске проверить оба сценария в тестовом Telegram-боте; после этого провести приёмку веба и восстановление незавершённых сессий.

## Decisions to finalize before dependent tasks

До интеграции выбрать развёртывание/версию PostgreSQL, способ веб-входа, AI-поставщиков, справочник сроков, численные пороги качества и политику данных. Эти решения не заменяются выбором по умолчанию без обоснования; задания tasks.md явно включают их подготовку. ВК, Android-клиент и семейный доступ остаются вне текущего объёма; их будущая поддержка не требует отказываться от общего API и адаптеров.

Выбор AI в ранних фазах начинается с бесплатных LLM и vision-моделей: сравниваются локальный запуск и внешние API с бесплатным доступом, лицензии, качество на разрешённых примерах, приватность медиа, лимиты, задержка и стоимость размещения. Отдельно фиксируются контракт подключения через порты, мониторинг, ограничения параллельности, таймауты, безопасные повторы и поведение при недоступности или исчерпании квоты (резервный вариант либо явное уточнение/ожидание). Ни один кандидат не считается выбранным до документированного решения; абсолютная бесперебойность не обещается.
