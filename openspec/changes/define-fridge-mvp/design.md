# Design

## Context

Пользователь описал два сценария: фотография видимых продуктов для выбора блюда и добавление покупок
фотографией или голосом. Текущий канал — Telegram; ВК только предполагается на будущее. Общая
инфраструктурная основа описана в [соседнем change](../establish-platform-foundation/design.md) .

Стек: FastAPI, Telegram, PostgreSQL, uv, QA только pytest. Android планируется в будущем
через общий API; разработка мобильного клиента сейчас исключена. Этот документ описывает будущую
реализацию; код, зависимости и внешние сервисы сейчас не создаются.

## Goals / Non-Goals

**Goals:** провести оба сценария через общее ядро, сохранить достоверность запасов при неоднозначном
вводе, обеспечить объяснимые оценки и расширяемость каналов.

**Non-Goals:** реализация ВК, семейный доступ, заказы продуктов, медицинские рекомендации,
автоматическое обучение общей модели, гарантии свежести по фото, автоматическое списание продуктов
при чтении рецепта.

## Decisions

### 1. Ports and adapters в модульном монолите

Внутреннее ядро содержит сущности и правила запасов, диалоговых сессий, подбора рецептов и
персональных исправлений. Прикладной слой координирует сценарии. Адаптеры переводят внешние
протоколы в типизированные команды и результаты ядра. Сборка приложения внедряет зависимости; ядро
не выбирает SDK через условие `if telegram` .

**Входной канал**

- **Ответственность порта:** Нормализованные события, идентичность, вложения и действия
- **Адаптер MVP:** Telegram
- **Возможное расширение:** ВК, только после отдельного запроса

**Выходной канал**

- **Ответственность порта:** Текст, карточки, кнопки, ошибки и progress
- **Адаптер MVP:** Telegram renderer/sender
- **Возможное расширение:** Другие представления без переписывания use cases

**Vision**

- **Ответственность порта:** Кандидаты продуктов, OCR-атрибуты, неопределённость
- **Адаптер MVP:** Выбран прямой Z.ai API: glm-4.6v-flash
- **Возможное расширение:** Замена через порт после отдельного выбора

**Speech-to-text**

- **Ответственность порта:** Транскрипция, неоднозначные участки, ошибка
- **Адаптер MVP:** Бесплатный облачный STT ещё не выбран
- **Возможное расширение:** Замена через независимый порт

**Recipe provider**

- **Ответственность порта:** Кандидат рецепта и происхождение
- **Адаптер MVP:** Выбран прямой Z.ai API: glm-4.7-flash
- **Возможное расширение:** Другой источник после отдельного выбора

**Shelf-life source**

- **Ответственность порта:** Средняя длительность, условия и источник
- **Адаптер MVP:** Версионируемый справочник
- **Возможное расширение:** Новый справочник с миграцией версии

**Persistence / jobs**

- **Ответственность порта:** Транзакции, репозитории, outbox, задачи
- **Адаптер MVP:** PostgreSQL; worker-процесс того же приложения
- **Возможное расширение:** Замена механизма доставки задач без утечки SDK в домен


Голосовое сообщение само по себе запускает сценарий добавления покупок: Telegram voice → проверка и
ограниченная загрузка аудио → speech-to-text с отметкой неясных участков → извлечение продуктов,
количества, объёма и явно названных сроков из транскрипта → проверка кандидатов, адресное уточнение
и запись однозначных позиций. Извлечение атрибутов может использовать общий LLM-порт или
специализированный парсер; ни STT, ни LLM не записывают запасы напрямую.

По уточнению пользователя модели работают только через облачные API, приложение — на обычном VPS.
Для речи в фазах 0–1 проверить готовые внешние STT на русских продуктовых названиях, числах,
единицах, шуме и коротких сообщениях. Локальный инференс и собственная адаптация/обучение не
планируются. При недоступности или неуверенной транскрипции сохранять безопасный путь уточнения или
текстового ввода без выдуманных покупок.

FastAPI и Telegram являются входами в одни прикладные операции, а не двумя реализациями
бизнес-логики. Оба бота вызывают прикладные операции; клиент не получает ключи AI. Реестр
доверенных адаптеров и dependency injection достаточны: динамическая загрузка плагинов, service mesh
и отдельные микросервисы не нужны для этих двух сценариев.

Будущий Android также обращается к версионируемому HTTP API и использует тот же User ID/холодильник.
Данные ответов структурированы: мобильному клиенту не нужно разбирать сообщения Telegram. Вход,
медиа-загрузка и асинхронные результаты отделены от протокола бота. Мобильный UI,
офлайн-синхронизация и push потребуют отдельного будущего change.

Контракт входного события: channel, installation ID, external event ID, external sender ID,
conversation ID, reply/action reference, timestamp и типизированное содержимое. Дедупликация
учитывает канал и установку бота. Идентичность пользователя определяется сервером после проверки
транспорта, а не из AI-ответа или поля запроса клиента.

Контракт результата содержит предметные данные и семантические действия: уточнить позицию, открыть
рецепт, сохранить рецепт, отменить конкретное добавление. Telegram-адаптер переводит их в
текст/кнопки, учитывая лимиты. Слишком длинный ответ делится адаптером; use case не знает о
количестве символов Telegram.

### 1.1. Почему выбраны GLM для MVP

Выбор пользователя: прямой облачный API Z.ai, `glm-4.7-flash` для текста и рецептов,
`glm-4.6v-flash` для фотографий. Это выбор по бюджету и нужным видам входных данных;
качество на примерах ingredia ещё не измерено.

- `glm-4.7-flash` обрабатывает текст: список продуктов, количество, единицы, уточнения
  и предложения рецептов. Расшифровку голосового она получает от отдельного STT.
- `glm-4.6v-flash` принимает изображения: продукты на полке и читаемые сведения упаковки.
  Вес, объём и точная дата не выводятся как факты, если их нельзя достоверно установить.
- В [прайсе Z.ai][glm-pricing] обе модели указаны как Free для входа и выхода.
  Платные FlashX и GLM-5.3-Flash не являются заменами по умолчанию.
- Прямой API Z.ai позволяет работать с выбранными моделями без посредника OpenRouter.
  Применяются квоты аккаунта Z.ai, а не квоты OpenRouter; безлимит не предполагается.
- Облачное размещение соответствует обычному VPS без GPU и локального инференса.
- Выбор не подтверждает лучшее качество относительно других моделей. Он задаёт набор
  для проверки до интеграции в пользовательские сценарии.

Перед включением выбранных моделей должны быть выполнены следующие проверки:

1. Подтверждены доступ из РФ, бесплатная тарификация обоих ID, квоты аккаунта
   и допустимые условия обработки пользовательских фото и текста.
2. На разрешённых русских примерах проверены названия продуктов, числа, единицы,
   конструкции «две пачки по литру», неоднозначности и даты на упаковках.
3. Для текста и фото отдельно определены пороги приёмки и измерено качество.
   Проверены схема ответа, обоснованные уточнения, задержка и расход на полный сценарий.
4. Проверены отказы: таймаут, исчерпание квоты, ошибочная схема, недоступная модель.
   Отказ не создаёт выдуманных позиций, дублирования покупок или платного переключения.
5. Рецепты проверяются на состав и доступность ингредиентов; сгенерированное происхождение
   обозначается явно. Сроки не назначаются только на основании ответа LLM.

Результаты фиксируются в отчёте до включения функций. При непрохождении проверки вопрос
выбора открывается повторно; автоматическая смена поставщика или тарифа запрещена.
Бесплатный облачный STT выбирается отдельно, голосовой сценарий остаётся в MVP.

[glm-pricing]: https://docs.z.ai/guides/overview/pricing

### 2. Разделение сценариев и состояние диалога

Режим выбирается кнопками «Что приготовить» / «Добавить покупки» или однозначным текстом, включая
транскрипцию голосового. Ясное «купил...» может сразу открыть добавление покупок без кнопки; при
неопределённости вопрос задаётся до изменения запасов. Намерение сохраняется в IntakeSession,
привязанной к пользователю, диалогу и сообщению.

Предлагаемые состояния сессии: received → processing → needs_clarification / partially_applied /
completed; отдельно failed и cancelled. Каждая позиция имеет собственный статус, чтобы уточнение
четвёртого продукта не добавляло первые три повторно.

Покупки: получение медиа → распознавание → нормализация → проверка → добавление однозначных позиций
→ сводка и вопросы по оставшимся. Продукт с неизвестным объёмом можно сохранить с неизвестным
атрибутом; неясная идентичность продукта требует ответа. Пользователь не подтверждает повторно
каждую очевидную позицию.

Рецепты: получение фото → распознавание → уточнение → сопоставление с холодильником → подбор →
карточки и избранное. Подбор и просмотр сами по себе не пополняют и не списывают запасы, не удаляют
невидимые продукты. «Добавить отсутствующий продукт» и подтверждённое «Закончилось» запускают
отдельные явные операции; «Не использовать сейчас» меняет только текущий подбор.

Вопрос содержит ссылку на конкретную позицию; ответы проверяют пользователя, сессию и её версию.
Новое сообщение не должно случайно отвечать на старый вопрос. При истёкшей/отменённой сессии бот
предлагает актуальное действие.

### 3. Модель запасов и происхождение атрибутов

**User / ChannelIdentity**

- **Значимые поля:** Internal user ID, display name, created_at, status, version, roles; channel,
  external sender ID
- **Инварианты:** Внешнее имя не является идентификатором; личные данные изолированы; blocked
  запрещает защищённые действия

**Product**

- **Значимые поля:** Canonical ID/name, category, aliases
- **Инварианты:** Нормализация названий не объединяет партии

**InventoryBatch**

- **Значимые поля:** Owner, product, count, per-package amount/unit, remaining amount/unit,
  added/opened dates, storage conditions, version
- **Инварианты:** Остаток неотрицателен; неизвестные числа допустимы

**AttributeEvidence**

- **Значимые поля:** Field, value, source, estimated flag, confidence/reason, reference
- **Инварианты:** Различаются слова пользователя, OCR, модель, справочник и персональная оценка

**ExpiryEstimate**

- **Значимые поля:** Date, date precision, source, anchor, storage assumptions, rule/catalog version
- **Инварианты:** Оценка не превращается в маркировку; дата покупки не считается датой производства

**IntakeSession / Item**

- **Значимые поля:** Owner, intent, source event, candidates, item status, applied operation ID,
  version
- **Инварианты:** Один item применяется один раз; вопросы адресные

**StockOperation**

- **Значимые поля:** ID, item/batch, delta, original version, idempotency key
- **Инварианты:** Отмена — компенсирующее изменение с проверкой версии

**RecipeSnapshot / Favorite**

- **Значимые поля:** Stable recipe ID/version, servings, ingredients, steps, provenance; owner +
  recipe version
- **Инварианты:** Избранное сохраняет рецепт, а не только временный AI-ответ

**CorrectionExample / Rule**

- **Значимые поля:** Owner, product/context, corrected field, scope, evidence, enabled/version
- **Инварианты:** Персональные поправки не становятся общими правилами


Числа хранятся без двоичных ошибок округления в количествах. Штуки, масса и объём — отдельные
размерности. «2 × 1 л» означает два пакета с общим объёмом 2 л, а не дополнительную третью запись
количества. Пересчёт литров в килограммы не допускается без предметных данных.

В PostgreSQL это реляционные таблицы с внешними ключами, CHECK/UNIQUE-ограничениями, числовыми
значениями точной десятичной арифметики и версией записи. Срок продукта хранится как календарная
дата с явно заданной точностью, момент события — как timestamp с временной зоной. JSONB подходит для
ограниченных дополнительных атрибутов и нормализованных AI-результатов, но права, остатки и даты не
прячутся в произвольный JSON. Полнотекстовый/семантический поиск и vector-расширения не добавляются
без измеренной потребности.

PostgreSQL содержит записи outbox и задач; для MVP предлагается worker с арендой задач из БД, без
обязательного Redis/RabbitMQ. Внешние вызовы не удерживают открытую транзакцию на всё время работы
AI: состояния и аренда фиксируются короткими транзакциями. Отдельный брокер возможен при
подтверждённой нагрузке. Медиа — во временном файловом/объектном хранилище; БД содержит ссылки,
владельца и срок очистки.

Партии с разными датами, условиями или неизвестным происхождением не сливаются автоматически. Поиск
рецепта может агрегировать совместимые доступные количества, сохраняя сведения о партиях и
неопределённости.

### 4. Сроки и персональные исправления

Приоритет данных: текущий явный ввод пользователя о конкретной партии → однозначная маркировка →
применимая персональная оценка → применимая справочная оценка → неизвестно. Исправление
пользователем маркировки сохраняется как пользовательский ввод с историей, а не переписывает
источник на «упаковка».

Для средней длительности необходимы категория, условия хранения и дата отсчёта. Если используется
дата добавления как приближение даты покупки, это явно показывается. При неизвестной дате
производства нельзя вычислять точный срок от неё. Вскрытие упаковки меняет контекст и может
потребовать новой оценки.

Конкретные числа сроков не придумываются в этом пакете: нужен выбранный справочник с происхождением
данных и областью применимости. Если оснований нет, система спрашивает или оставляет срок
неизвестным.

Первая версия «обучения» — поиск похожих персональных исправлений и типизированные правила, а не
обновление весов модели. Совпадение контекста, версия и объяснение доступны. Одиночное исправление —
пример для предположения; для устойчивого предпочтения требуется подтверждённый повторяющийся
контекст либо явное действие пользователя «использовать обычно». Сброс отключает будущее
использование, не пересчитывает существующие партии.

Глобальное обучение на фотографиях и голосе не выполняется по умолчанию. Справочные и персональные
сроки остаются оценками и не подтверждают безопасность продукта.

### 5. Подбор и избранное

Сопоставление использует нормализованный продукт и признаки; несколько подходящих партий не требуют
выдумывать, какая именно упаковка на фото. Если это важно для остатка или срока, задаётся уточнение.
Фото — частичное наблюдение: отсутствие продукта в кадре ничего не говорит о его отсутствии в
холодильнике.

В подбор передаётся снимок подтверждённых ингредиентов, доступных запасов и неопределённостей.
Основной приоритет — продукты с фото; остальные запасы могут дополнять блюдо. Генератор не объявляет
отсутствующий ингредиент доступным. Любые базовые ингредиенты, замены и требуемые количества
показываются явно.

Результат проверяется по схеме и сопоставляется с запасами после генерации. Классы доступности: есть
достаточно; есть, количество неизвестно; подтверждено на фото, ещё не учтено; отсутствует; исключено
из доступных по сроку. При просмотре сохранённого рецепта доступность вычисляется заново, а сам
рецепт не генерируется повторно.

Запасы не списываются от факта просмотра. Списание по приготовлению и масштабирование порций с
автоматическим резервированием могут стать отдельной фичей.

### 5.1. Коррекция из рецепта и исключение на один подбор

Пользователь согласовал две идеи из [discovery](../../../docs/product-discovery-2026-10-29.md) :
исправление устаревших запасов при выборе блюда и объяснимый приоритет близкого срока. Они входят в
фазу 3 текущего change.

Действие «Закончилось» открывает подтверждение с выбранными партиями и прежним/новым остатком. При
нескольких партиях пользователь выбирает затронутые; остальные сохраняются. Неоднозначное «молока
нет» сначала предлагает два действия: исправить запасы или временно исключить продукт. Невидимость
продукта на фото не вызывает коррекцию.

Подтверждённая коррекция — отдельная типизированная StockOperation с проверкой владельца, версии и
идемпотентности. Отмена выполняет компенсирующую операцию и восстанавливает прежний остаток только
при отсутствии последующих изменений; иначе показывается конфликт. Коррекция не является обучением
персонального правила. После неё и после успешной отмены доступность и подбор пересчитываются. Сбой
подбора не откатывает уже подтверждённый остаток: пользователь видит сохранённую коррекцию,
неактуальность старого списка и возможность повторить только подбор.

«Не использовать сейчас» исключает из текущих рекомендаций рецепты, требующие выбранный
нормализованный продукт, включая его подтверждение на фото, без изменения партий. Исключения
привязаны к владельцу и сессии подбора, видимы и снимаются пользователем. Они не записываются как
постоянные предпочтения и не переносятся в новый независимый подбор.

Порядок рецептов сначала учитывает соответствие запросу/подтверждённым продуктам фото и доступность
ингредиентов. При прочих равных ближняя неистёкшая подтверждённая дата повышает приоритет; причина
содержит продукт, дату и источник. Оценочные даты отображаются отдельно и не подменяют
подтверждённую срочность; неизвестные даты не дают приоритета. Истёкшие партии исключаются по
действующему правилу recipe-discovery. Числовое окно «скоро» и дополнительные веса ранжирования
уточняются перед реализацией; сценарии сравнения более ранних подтверждённых дат проверяются
независимо от них. Проактивные Telegram-напоминания не входят в эти две возможности.

Все предметные действия доступны в пользовательском Telegram-боте. UX включает подтверждение, отмену
подтверждения, загрузку пересчёта, успех, конфликт версии, сбой подбора и отмену сохранённого
изменения. Подписи прямо сообщают, меняется ли запас; состояния и результаты обозначаются текстом с
понятными кнопками. Приёмка — pytest для серверных правил и ручные UX-сценарии без
скриншотного тестирования.

### 6. Безопасность, приватность и надёжность

Общие требования безопасности и устойчивой доставки берутся из foundation. Дополнительно:

- Все stock/favorite/correction операции получают пользователя из проверенного контекста. AI выдаёт
  только данные-кандидаты, а изменения выполняют типизированные серверные команды после проверки.
- Prompt injection из упаковки, транскрипции или ответа модели не может расширить набор операций.
  Модель не получает секреты бота, произвольный SQL или сетевые инструменты для выполнения команд.
- Аккаунт разрешается по проверенному числовому Telegram ID, не username. Начальный администратор
  назначается доверенной конфигурацией TELEGRAM__ADMIN__USER_IDS; пустой список запрещает доступ.
  Токен админ-бота и /start не выдают прав. Связывание с ВК отложено.
- Фото и голос скачиваются только через доверенный Telegram-адаптер. Проверяются фактический тип,
  размер, декодирование и лимит длительности; EXIF и лишние метаданные не передаются далее без
  необходимости.
- Предлагаемые стартовые ограничения приложения: до 10 MiB на медиа, голос до 120 секунд, временные
  копии не дольше 24 часов после завершения или сбоя. Это проектные значения для обсуждения, а не
  утверждение о лимитах Telegram. До реализации проверить совместимость выбранных API и стоимость
  обработки.
- TTL-очистка включает успешные, ошибочные и прерванные задания; логируется результат удаления без
  содержимого файла. Политика внешнего AI-поставщика проверяется отдельно: локальное удаление не
  означает удаление на стороне поставщика.
- Транзакция записи партии, результата item, операции и outbox предотвращает повторное добавление
  при потере ответа. Повтор отправки сводки не выполняет операцию stock заново.
- Для внешних AI-вызовов используются timeout, ограниченный retry для безопасных запросов, лимит
  параллельности и квоты по пользователю. Сбой не превращается в выдуманные ингредиенты или частично
  скрытый успех.

Детали Telegram берутся из официальной [Bot API](https://core.telegram.org/bots/api) :
преобразование photo/voice, загрузка через getFile, идентификаторы обновлений и webhook secret.
Токен может присутствовать в URL Telegram API и загрузки файлов; такие URL должны
удаляться/маскироваться в логах HTTP-клиента. Конкретные настройки и лимиты фиксируются в provider
change перед реализацией.

### 7. UX

В Telegram основные действия: «Что приготовить», «Добавить покупки», «Мой холодильник», «Избранное».
«Личный кабинет» показывает профиль, статус и персональные поправки. «Мой холодильник»
открывает партии, количество, сроки и редактирование. В разделах есть «Назад» и «В меню».
Сценарии описаны в specs/telegram-user-navigation/spec.md.

После добавления сводка разделяет «добавлено», «нужно уточнить», «не распознано» и даёт действие
исправления/отмены конкретного ввода. Оценки объёма и срока обозначаются рядом со значением. Вопросы
короткие, по конкретной позиции, с возможностью ответить текстом.

Карточка рецепта не скрывает недостающие ингредиенты за кнопкой приготовления. Пустое избранное и
пустой холодильник объясняют следующий шаг. Состояния загрузки, ошибки, повтора и частичного успеха
различаются текстом. Telegram использует короткие карточки, пагинацию и понятные подписи кнопок;
скриншотных тестов нет.

### 8. QA и связь со спецификациями

**fridge-inventory**

- **Автоматизация только pytest:** Изоляция, партии, единицы, неизвестные атрибуты, источники дат,
  конфликты
- **Ручная приёмка:** Понятность карточки и обозначений оценки

**multimodal-intake**

- **Автоматизация только pytest:** Fake vision/STT, уточнение, частичный успех, дубли, отмена, сбой
- **Ручная приёмка:** Фото/голос в Telegram, понятность вопросов

**recipe-discovery**

- **Автоматизация только pytest:** Частичная фотография, missing ingredients, личный список/snapshot
  избранного, отсутствие списания, коррекция и сроки
- **Ручная приёмка:** Карточка, сохранённое состояние, пустое избранное и ошибки

**personal-corrections**

- **Автоматизация только pytest:** Контекст, приоритет маркировки, изоляция, сброс
- **Ручная приёмка:** Объяснение и управление поправками

**messaging-channels**

- **Автоматизация только pytest:** Контракт Telegram/fake adapter, идентичность, лимиты медиа,
  injection, outbox
- **Ручная приёмка:** Сквозной диалог и проверенная Telegram-идентичность

**user-administration**

- **Автоматизация только pytest:** Роли, список, блокировка по каналам/worker, версии, аудит без
  личного содержимого
- **Ручная приёмка:** Поиск, карточка, подтверждение/отмена, ошибки и клавиатура


Тесты опираются на фиксированные ожидаемые результаты и искусственные ответы поставщиков. Качество
реального vision/STT/рецептов измеряется отдельно на согласованном наборе разрешённых примеров;
pytest может запускать такую оценку с явной конфигурацией. Метрики: правильность идентификации,
извлечение единиц/дат, доля нужных уточнений и соответствие ингредиентов. Порог приёмки задаётся до
реализации выбранного поставщика, а не объявляется достигнутым без измерений.

Тесты реальных облачных моделей не входят в обычный запуск: они требуют сети, расходуют квоты и
могут быть недетерминированными. Browser runners и скриншотные сравнения не вводятся.
Ruff/mypy проверяют Python. Диалоги принимаются вручную в Telegram без скриншотных тестов.
Будущий ВК проверяется сейчас только fake adapter; реализация отложена.

### 9. Админка управления пользователями в MVP

Подтверждённый пользователем объём — отдельный Telegram-бот управления пользователями.
Для MVP предлагаются постраничный список, поиск по ID/имени, фильтр active/blocked, карточка
аккаунта,
блокировка/разблокировка обычного пользователя и история административных действий. Создание
аккаунтов остаётся частью выбранного входа; редактирование чужих продуктов, массовые рассылки,
удаление данных и управление административными ролями через UI не добавляются этим требованием.

В User добавляются status, created_at и version, а полномочия выдаются доверенным серверным
механизмом. Отдельное право управления пользователями не наследуется из роли оператора подключений и
не даёт доступа к чужому холодильнику/избранному/медиа. Начальный администратор назначается
документированной доверенной процедурой развёртывания после выбора аутентификации; регистрация и
редактирование профиля не принимают административные полномочия из клиента. Админка MVP блокирует
только обычные аккаунты: свой и другие административные аккаунты защищены серверной проверкой.

Отдельный админ-бот вызывает административные операции общего прикладного ядра. Карточка содержит
минимальные метаданные аккаунта, роли и наличие привязок, не содержимое личных данных. Результат
поиска сохраняет фильтры при ошибке. Изменение статуса требует подтверждения и причины, версии цели
и ключа идемпотентности. Журнал административных действий расширяет общие правила аудита foundation:
запись actor/target/action/reason/result согласуется транзакционно с изменением статуса, без тел
сообщений и секретов.

Проверка active применяется при каждом действии пользовательского бота
независимо от существующей сессии. Worker проверяет статус перед внешним вызовом и повторно перед
применением результата;
транзакции изменения личных данных сериализуются с изменением статуса аккаунта. Блокировка,
зафиксированная первой, запрещает последующее применение результата, не откатывая уже завершённые до
неё операции. Ожидающие задания отменяются по блокировке, исходящие сообщения перед отправкой
перепроверяют доступ; уже начатую внешнюю отправку нельзя гарантированно отозвать. Разблокировка не
повторяет отменённые операции автоматически.

QA: pytest для прав всех административных маршрутов, подмены роли, минимизации данных,
подтверждения/идемпотентности/версий, атомарности аудита и гонки блокировки с worker; ручная
проверка админ-бота для списка, фильтров, подтверждения, отказа и неизвестного исхода.
Реализация админки входит в фазу 5; базовые роли/статус и выбор административного входа — в фазу 1.

## Risks / Trade-offs

- Фото не гарантирует точность идентичности, веса и свежести → кандидатные данные, неизвестные
  значения, адресные уточнения и происхождение атрибутов.
- Средний срок может не соответствовать конкретной партии → явная оценка, условия и приоритет
  маркировки; без обещаний безопасности.
- Простые персональные правила менее гибки, чем обучение модели → зато они объяснимы, изолированы и
  удаляемы; сначала измеряется их эффект.
- Асинхронные сообщения могут повторяться и приходить поздно → версии сессий, item-level
  идемпотентность и транзакционный outbox.
- Единственный реальный канал может скрыть утечку Telegram-типов в ядро → общий contract-набор с
  fake adapter и проверка границ импортов при ревью.

## Уточнение архитектуры 2026-10-30

Пользовательский и административный боты используют общий Telegram SDK и низкоуровневые
компоненты, но отдельные маршрутизаторы и политики доступа. Административные обработчики
планируются в adapters/telegram_admin. Общее ядро не зависит от SDK. Админ-бот не получает
доступ к чужим запасам и медиа. Ключ события включает роль подключения/бота и update_id.

Для каждого токена работает один polling-consumer; жизненный цикл и готовность различаются.
Сбой админ-бота не должен останавливать пользовательские сценарии. Transport обоих ботов, меню, кабинет и PostgreSQL реализованы в текущем MVP.
Legacy-фото-проба без DATABASE__URL запускает только пользовательского бота.


## Административное меню — 2026-10-30

Административный адаптер разделён на access, menu, models, views, navigation и обработчики
подтверждений. Общие операции AccountService возвращают только метаданные аккаунта.
Постоянная клавиатура открывает списки и поиск, inline-кнопки — страницы, фильтры и карточки.
Контекст FSM хранит запрос, фильтр, страницу и краткоживущий выбор действия отдельно для
каждого администратора и бота. Кнопки списка содержат непрозрачный идентификатор контекста;
знание callback не заменяет проверку доверенного числового ID и текущего доступа на сервере.

Меню/возврат отменяют незавершённые действия. Изменение статуса повторно проверяет версию
аккаунта; новый статус и аудит сохраняются существующей транзакционной операцией.
Самоблокировка и блокировка других доверенных администраторов через карточку недоступны.
Просмотр их метаданных разрешён. Отчёт истории и расширенные операции остаются вне этого изменения.

## Реализованный срез: сроки, рецепты и компактный холодильник — 2026-10-30

PurchaseContents сохраняет распознавание и отдельные ExpiryEstimate. Правила версионированы
в accounts/data/expiry_v1.json; нет генерации срока моделью и обратного заполнения старых партий.
Покупки подтверждаются с оценками или без них; прежние черновики читаются без новых оценок.

RecipeGenerator реализован в отдельных пакетах Groq и Z.ai. RecipeService проверяет доступ
до облачного запроса и перед фиксацией снимков. Наличие ингредиентов вычисляется приложением:
сравнение названий консервативное, единицы приводятся только внутри одной размерности.
Истёкшие даты исключаются независимо от происхождения. Генерация ограничена 60 партиями.

Recipe хранит снимок рецепта и флаг избранного под владельцем. Повторное сохранение задаёт
желаемое состояние, открытие пересчитывает наличие без новой генерации и изменения остатков.
Новое успешное поколение заменяет только несохранённые карточки владельца.

Telegram показывает шесть кнопок партий; подробности и страницы редактируют исходный экран.
Фото принимается обычным сообщением или JPEG/PNG-документом. Для Groq-фото выбран JSON mode:
строгий vision-формат воспроизвёл json_validate_failed. Локальная проверка Pydantic обязательна.
Это не автоматический fallback: режим заранее задан для типа операции.

Голос, сверка фотографии полки, исправления остатков и персональное обучение ещё не реализованы.
Полные пункты соответствующих фаз не считаются закрытыми этим срезом.
