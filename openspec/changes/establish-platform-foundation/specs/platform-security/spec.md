# Platform security

## Purpose

Общие требования к границам доступа, защите секретов и обработке недоверенных данных при подключении
и эксплуатации ботов.

## ADDED Requirements

### Requirement: Resource authorization

Система SHALL проверять идентичность и разрешение на целевой ресурс для каждой операции управления
подключением. При отсутствии разрешения доступ SHALL быть закрыт независимо от видимости элементов
UI.

#### Scenario: Unauthenticated management request
- **WHEN** неаутентифицированный клиент обращается к управлению подключениями
- **THEN** API отклоняет запрос и не выполняет операцию.

#### Scenario: Foreign connection identifier
- **WHEN** клиент подставляет идентификатор подключения, к которому у него нет доступа
- **THEN** API не раскрывает сведения о подключении и не изменяет его состояние.

#### Scenario: Worker receives a queued job
- **WHEN** worker обрабатывает сохранённую задачу
- **THEN** он проверяет привязку задачи к разрешённому подключению и его актуальное состояние до
  внешнего вызова.

### Requirement: Credential confidentiality

Система SHALL хранить секреты подключений в зашифрованном виде либо специализированном хранилище
секретов, отдельно от ключей доступа к ним. API, логи, аудит и сообщения об ошибках SHALL не
возвращать секрет целиком или частично.

#### Scenario: Read connection
- **WHEN** пользователь получает сведения о подключении
- **THEN** ответ содержит признак наличия секрета, но не исходное значение или его фрагмент.

#### Scenario: Provider error contains a token
- **WHEN** провайдер возвращает диагностический ответ с токеном
- **THEN** пользователю и в журналы попадает только безопасный код и очищенное описание ошибки.

#### Scenario: Secret store unavailable
- **WHEN** секрет недоступен из защищённого хранилища
- **THEN** операция завершается безопасной ошибкой без перехода к незашифрованному резервному
  хранению.

### Requirement: Credential replacement

Система SHALL проверять новые учётные данные перед заменой и после успешной замены использовать
только новую версию для новых операций. Ошибка проверки SHALL не уничтожать предыдущую рабочую
конфигурацию.

#### Scenario: Failed replacement
- **WHEN** новые учётные данные не проходят проверку
- **THEN** старые учётные данные остаются текущими, а новые не активируются.

#### Scenario: Successful replacement
- **WHEN** новые учётные данные проверены и замена подтверждена
- **THEN** новые операции используют новую версию, а завершение уже начатых операций учитывается
  отдельно.

### Requirement: Trusted inbound events

Система SHALL принимать события только через включённый транспорт адаптера с предусмотренной
провайдером проверкой подлинности. Если достаточного механизма проверки нет, транспорт SHALL
оставаться выключенным до явного решения в спецификации провайдера.

#### Scenario: Invalid webhook authentication
- **WHEN** запрос webhook не проходит проверку подписи или предусмотренного провайдером секрета
- **THEN** событие не ставится на обработку и не вызывает бизнес-действий.

#### Scenario: Replay outside validity period
- **WHEN** провайдер поддерживает временную подпись и её срок допустимости истёк
- **THEN** событие отклоняется до обработки.

### Requirement: Bounded untrusted input

Система SHALL проверять схему, размер и допустимые значения входных данных, ограничивать частоту
запросов и ресурсы обработки. Содержимое событий SHALL считаться данными и не предоставлять права на
выполнение кода или административных действий.

#### Scenario: Oversized payload
- **WHEN** размер события превышает настроенный предел
- **THEN** обработка отклоняется до дорогостоящего разбора и не запускает операции бота.

#### Scenario: HTML or instruction in message
- **WHEN** сообщение содержит HTML, скрипт или текст с инструкцией повысить привилегии
- **THEN** интерфейс отображает его как безопасный текст, а система не меняет права и не выполняет
  код.

### Requirement: Restricted outbound destinations

Система SHALL ограничивать исходящие подключения разрешёнными адресами провайдеров и проверять TLS.
Произвольные пользовательские адреса, небезопасные перенаправления и обращения к внутренним
служебным адресам SHALL быть запрещены по умолчанию.

#### Scenario: User supplies internal URL
- **WHEN** параметр подключения указывает на loopback, приватный или metadata-адрес вне разрешённой
  конфигурации
- **THEN** система отклоняет его до сетевого обращения.

### Requirement: Security audit without payload leakage

Система SHALL записывать субъекта, действие, ресурс, время, результат и идентификатор корреляции для
изменений подключений и отказов доступа. Аудит SHALL не содержать секреты и тела сообщений; доступ к
нему SHALL проверяться отдельно.

#### Scenario: Connection disabled
- **WHEN** пользователь успешно отключает подключение
- **THEN** сохраняется запись аудита с его идентичностью, подключением и результатом операции.

#### Scenario: Unprivileged audit access
- **WHEN** клиент без права чтения аудита запрашивает журнал
- **THEN** система отклоняет запрос без раскрытия записей.
