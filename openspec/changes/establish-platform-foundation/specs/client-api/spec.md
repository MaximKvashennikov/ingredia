# Client API

## Purpose

Общий контракт доступа к ingredia для серверных операций и будущего Android-клиента, сохраняющий
одни данные и
правила независимо от канала.

## ADDED Requirements

### Requirement: Versioned machine-readable contract

Система SHALL предоставлять версионируемый HTTP API с машиночитаемой схемой запросов, ответов и
ошибок. Изменение смысла или удаление существующего поля SHALL требовать новой несовместимой версии
и плана миграции.

#### Scenario: Compatible API extension
- **WHEN** сервер добавляет необязательное поле ответа в текущей версии
- **THEN** прежние поля сохраняют типы и смысл, а существующий клиент продолжает выполнять свой
  сценарий.

### Requirement: Channel-independent user identity

Система SHALL связывать данные с внутренней идентичностью пользователя, независимой от Telegram. Все
клиентские способы входа SHALL приводить к одинаковой проверке прав на его холодильник и избранное.

#### Scenario: Web and bot access the same account
- **WHEN** пользователь с доказанной привязкой открывает холодильник из пользовательского бота и
  worker
- **THEN** он видит одни актуальные данные и не получает дополнительных прав из-за выбранного
  клиента.

### Requirement: Structured domain responses

Система SHALL возвращать структурированные данные продуктов, рецептов и операций, а не требовать
разбора текста сообщений бота. Единицы, источники оценок, даты, ошибки и правила пагинации SHALL
быть описаны в контракте.

#### Scenario: Client renders an estimated expiry
- **WHEN** клиент получает продукт с оценочным сроком
- **THEN** ответ содержит отдельные значения даты, источника и признака оценки, позволяя корректно
  отобразить их без анализа текста Telegram.

### Requirement: Retry-safe client operations

Система SHALL поддерживать устойчивую идентичность изменяющей операции и получение её результата
после потери соединения. Повтор с тем же ключом и содержимым SHALL не создавать повторное изменение
запасов.

#### Scenario: Client reconnects after submission
- **WHEN** клиент теряет ответ после сохранения покупки и повторяет запрос с тем же ключом
- **THEN** он получает результат исходной операции без второй записи покупки.
