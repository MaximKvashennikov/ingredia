# Connection management UX

## Purpose

Понятное управление подключениями ботов с доступными формами, честным отображением состояний и восстановлением после ошибок.

## ADDED Requirements

### Requirement: Connection list states

Интерфейс SHALL различать загрузку, пустой список, ошибку получения данных и доступные подключения. Для подключения SHALL отображаться провайдер, имя, статус и время последней проверки, если оно известно.

#### Scenario: Empty list
- **WHEN** загрузка успешно завершена и подключений нет
- **THEN** пользователь видит объяснение и доступное ему действие создания подключения.

#### Scenario: Fetch failure
- **WHEN** загрузка завершается ошибкой
- **THEN** интерфейс показывает ошибку и действие повтора, не выдавая её за пустой список.

### Requirement: Guided connection form

Интерфейс SHALL запрашивать только поля выбранного провайдера, указывать обязательность и показывать ошибки рядом с полями. Введённый секрет SHALL не сохраняться в URL, браузерном постоянном хранилище или аналитике.

#### Scenario: Invalid field
- **WHEN** обязательное поле отсутствует либо имеет неверный формат
- **THEN** пользователь получает конкретное объяснение и сохраняет остальные несекретные значения формы.

#### Scenario: Form closed
- **WHEN** пользователь покидает или закрывает форму
- **THEN** введённый секрет удаляется из управляемого приложением состояния формы и не восстанавливается автоматически.

### Requirement: Honest operation feedback

Интерфейс SHALL показывать состояние выполнения и подтверждать успех только после ответа сервера. Пока запрос выполняется, повторная отправка тем же элементом управления SHALL блокироваться.

#### Scenario: Slow provider verification
- **WHEN** проверка подключения ещё выполняется
- **THEN** интерфейс показывает ожидание и не отображает подключение как активное.

#### Scenario: Lost response
- **WHEN** ответ сервера потерян после отправки изменяющего запроса
- **THEN** интерфейс сообщает о неизвестном результате и обновляет состояние ресурса перед предложением повторить действие.

### Requirement: Understandable disable action

Интерфейс SHALL перед отключением объяснять остановку новых операций и возможность завершения уже отправленных, затем запрашивать подтверждение пользователя.

#### Scenario: User cancels disable
- **WHEN** пользователь отменяет подтверждение
- **THEN** запрос отключения не отправляется и подключение остаётся в прежнем состоянии.

### Requirement: Keyboard and assistive technology access

Интерфейс SHALL обеспечивать управление клавиатурой, видимый фокус, подписи полей и программно доступные сообщения ошибок. Статусы SHALL различаться текстом, а не только цветом.

#### Scenario: Keyboard-only connection flow
- **WHEN** пользователь проходит форму, проверку и подтверждение только клавиатурой
- **THEN** все действия достижимы в логичном порядке без ловушки фокуса, а результат доступен вспомогательным технологиям.

### Requirement: Responsive management layout

Интерфейс SHALL сохранять доступность основных действий и содержимого при ширине 320 CSS-пикселей и увеличении текста до 200 процентов без обязательной горизонтальной прокрутки основного экрана.

#### Scenario: Narrow viewport
- **WHEN** экран управления используется при ширине 320 CSS-пикселей
- **THEN** названия, состояния, ошибки и действия остаются читаемыми и доступны без перекрытия элементов.
