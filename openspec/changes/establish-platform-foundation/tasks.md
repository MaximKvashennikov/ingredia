# Tasks

Статус: предварительный план будущей реализации. Ни одна задача ниже не выполняется в текущем запросе. Сначала требуется заполнить продуктовый контекст, уточнить зависимые changes и получить запрос пользователя на реализацию. Проверка формата OpenSpec не снимает эти условия.

## 1. Основа и границы доступа

- [ ] 1.1 После определения продукта и доступа закрепить версии runtime, uv-окружение и структуру FastAPI/React; проверка: чистая установка по lock-файлам, сборка frontend и запуск pytest.
- [ ] 1.2 Реализовать контракт идентичности и проверки прав из отдельного change доступа; проверка: pytest для отсутствующей идентичности, чужого ресурса и разрешённой операции.
- [ ] 1.3 Зафиксировать схему API подключений и единые безопасные ошибки; проверка: pytest соответствия ответов схеме и отсутствия секретов.
- [ ] 1.4 Реализовать версионируемый OpenAPI-контракт и общий principal клиентов; проверка: pytest схем, совместимости ответов, пагинации, идемпотентности и одинаковых прав независимо от способа входа; Android не разрабатывается.
- [ ] 1.5 Подготовить Dockerfile для API/worker и frontend, Compose-конфигурации для локального запуска и первого сервера с PostgreSQL; проверка: `docker compose config`, чистая сборка и запуск, pytest на PostgreSQL, сохранность данных после пересоздания контейнера, отсутствие секретов в образах и внешнего доступа к БД.

## 2. Подключения и устойчивые операции

- [ ] 2.1 Реализовать Connection, Inbound event и Operation в PostgreSQL с миграциями и уникальными ограничениями; проверка: pytest конкурентной регистрации одинакового события и отката незавершённой транзакции на PostgreSQL.
- [ ] 2.2 Реализовать реестр и контракт адаптера с тестовым провайдером; проверка: pytest для поддерживаемой и запрещённой capability.
- [ ] 2.3 Реализовать проверку, включение и отключение подключения; проверка: pytest всех переходов таблицы design и обработки таймаута проверки.
- [ ] 2.4 Реализовать безопасное хранение и замену секрета; проверка: pytest успешной/неуспешной замены и сбоя хранилища секретов.
- [ ] 2.5 Реализовать идемпотентность изменяющих API-запросов; проверка: pytest повторного ключа с одинаковыми и разными данными.
- [ ] 2.6 Реализовать устойчивый приём событий и выдачу задач worker; проверка: pytest сбоя хранилища, падения worker и восстановления аренды.
- [ ] 2.7 Реализовать ограниченные повторы и результат unknown; проверка: pytest с управляемым временем, исчерпанием бюджета и неопределённым исходом отправки.
- [ ] 2.8 Реализовать согласование отключения с выдачей операций worker; проверка: pytest гонки отключения/старта, отмены очереди и учёта уже начатой операции.

## 3. Первый провайдер и безопасность

- [ ] 3.1 По отдельной спецификации выбранного провайдера реализовать проверку credentials и нормализацию событий; проверка: общий pytest contract-набор и фикстуры протокола без реальных секретов.
- [ ] 3.2 Реализовать выбранный транспорт и проверку подлинности; проверка: pytest валидного/невалидного webhook либо polling с восстановлением позиции, согласно capability провайдера.
- [ ] 3.3 Реализовать лимиты входа и ограничения исходящей сети; проверка: pytest oversized payload, rate limit, запрещённого адреса и редиректа.
- [ ] 3.4 Реализовать безопасный аудит; проверка: pytest полноты записей, атомарности изменения и аудита, отказа доступа к журналу и отсутствия токена/payload.
- [ ] 3.5 Проверить интеграцию в тестовом окружении выбранной платформы в согласованных пределах; проверка: отчёт smoke-сценария через pytest с указанием выполненных внешних действий и результата.

## 4. UX управления подключениями

- [ ] 4.1 Уточнить UX по продуктовым сценариям и доступным релевантным skills, затем реализовать список и форму; проверка: ручное прохождение empty/loading/error/success-состояний.
- [ ] 4.2 Реализовать обратную связь асинхронных действий и подтверждение отключения; проверка: ручные сценарии задержки, потерянного ответа, отмены и неизвестной доставки.
- [ ] 4.3 Проверить доступность и адаптивность; проверка: клавиатура, видимый фокус, доступные подписи/сообщения, ширина 320 CSS px и текст 200%, без скриншотных тестов.

## 5. Приёмка и эксплуатация

- [ ] 5.1 Связать каждое требование и сценарий всех spec.md этого change с pytest-проверкой либо явно ручной UX-приёмкой; проверка: заполненная матрица покрытия без необъяснённых пропусков.
- [ ] 5.2 Проверить основной согласованный продуктовый сценарий и отказы; проверка: итог `uv run pytest`, сборка/typecheck frontend и отчёт ручной приёмки с ограничениями.
- [ ] 5.3 Описать и проверить восстановление, ротацию секретов, сроки хранения и обработку unknown; проверка: протокол упражнений в тестовом окружении без production-секретов.

## Workflow follow-up

- После реализации и проверки всех задач сверить результат с согласованными требованиями и только затем архивировать change и обновить базовые specs.
- До реализации сохранять этот change как проект; завершение подготовки документации не отмечает перечисленные задачи выполненными.
