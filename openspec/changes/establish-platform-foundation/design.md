# Design

## Context

При подготовке основы существующих API, данных и миграций нет; настроена лишь загрузка Telegram-токена. Обязательные технологии заданы пользователем: FastAPI, React/TypeScript, uv, pytest и Docker для запуска. Мотивация и границы — в [proposal.md](proposal.md).

Документ описывает предлагаемую архитектуру общего подключения ботов. Предметная область — виртуальный холодильник, канал MVP — Telegram; ВК только возможное расширение. Продуктовые требования и предлагаемая модель личного холодильника описаны в change `define-fridge-mvp`. Зависимые решения перечислены в [product-brief](../../../docs/product-brief.md); готовность этого файла не означает разрешение на реализацию MVP.

## Goals / Non-Goals

**Goals:** выделить границу провайдера, сохранить проверяемость без внешней сети, обработать повторы и неопределённость доставки, защитить секреты и определить честные пользовательские состояния.

**Non-Goals:** реализация предметных процессов внутри провайдерских адаптеров, загрузка пользовательского кода, выбор конкретного сервера и написание приложения в текущем этапе. Распознавание и рецепты описаны отдельно в `define-fridge-mvp`.

## Decisions

### 1. Модульное приложение и отдельное выполнение интеграционных операций

Предлагается начать с модульного монолита FastAPI: HTTP-слой, прикладные операции, доменные правила, адаптеры и инфраструктура хранения. React/TypeScript обращается только к API; токены провайдера после ввода не возвращаются в браузер. Долгие внешние операции исполняются worker-процессом из того же проекта.

Такой вариант позволяет тестировать ядро отдельно от сети и масштабировать worker без распределения каждого модуля в отдельный сервис. Микросервисы добавят преждевременные сетевые и эксплуатационные зависимости; выполнение долгих задач только внутри HTTP-запроса плохо переносит перезапуск и таймауты. Worker запускается как отдельный сервис Compose из того же приложения; транспорт очереди выбирается после оценки нагрузки.

Логическое направление зависимостей: UI → HTTP API → прикладные операции → контракт адаптера → конкретный провайдер. Входящее событие проходит проверку адаптера → устойчивую регистрацию → worker → прикладную операцию. Доменные правила не импортируют SDK конкретной платформы.

### 2. Реестр доверенных адаптеров

Адаптер описывает провайдера, поддерживаемые возможности, схему настроек и операции проверки подключения, нормализации событий и выполнения поддерживаемого действия. Проверка подлинности webhook применяется к исходным байтам до преобразования payload.

Webhook и polling — альтернативные способности провайдера. Не требуется поддерживать оба для каждого бота. Спецификация первого адаптера определит транспорт, подпись/секрет, timestamp, лимиты, ключ события, порядок событий и политику повторов.

Реестр включает только поставляемые приложением адаптеры. Импорт по имени от пользователя, выполнение произвольного кода и загрузка плагинов не предусматриваются. Универсальный HTTP-прокси отвергнут: он размывает полномочия и создаёт SSRF-риски.

### 3. Данные и API-контракт

Основная СУБД — PostgreSQL по предложению пользователя. Логические сущности:

| Сущность | Минимальные сведения | Инвариант |
| --- | --- | --- |
| Connection | ID, provider, имя, ссылка на область доступа, status, external bot ID, secret reference/version, timestamps, safe error | Секрет не включается в ответ API; область доступа задаётся сервером |
| Inbound event | Connection ID, provider event ID, received time, processing state, ограниченный срок хранения | Уникальность ключа дедупликации обеспечивается атомарно |
| Operation | ID, connection ID, action, idempotency key, state, attempts, deadline, correlation ID | Повтор безопасной команды не создаёт независимый побочный эффект |
| Audit record | Subject, action, resource ID, timestamp, result, correlation ID | Нет секретов и тел сообщений |

PostgreSQL хранит связи, транзакционные изменения, уникальные ключи событий и outbox. Реляционные столбцы используются для идентичности, прав, количеств и дат; JSONB — для ограниченных версионируемых метаданных, а не вместо схемы. Фото/голос хранятся отдельно с TTL; в БД — ссылки и статусы очистки. Сроки хранения ключей дедупликации и аудита определяются до реальных данных. Payload не сохраняется без необходимости.

Выбор PostgreSQL обоснован поддержкой [транзакционной изоляции](https://www.postgresql.org/docs/current/transaction-iso.html) и [JSONB](https://www.postgresql.org/docs/current/datatype-json.html). Одна транзакция объединяет изменение доменных данных, запись результата и outbox; уникальные ограничения защищают от дублей. Конкурентные изменения требуют проверки версии или блокировки строки: сама транзакция не устраняет все гонки автоматически.

Предлагаемые операции API: список и сведения подключений, создание, проверка, замена секрета, отключение и получение результата операции. Стабильные коды ошибок отделены от локализованного текста; ответы не включают stack trace или сырой ответ провайдера. Версионируемый контракт API и его схема описываются перед реализацией; конкретные URL не зафиксированы.

Для пользовательских клиентов предлагается HTTPS JSON API с префиксом `/api/v1` и OpenAPI-схемой. Веб React и будущий Android используют один контракт, а бот — те же прикладные операции через свой адаптер. Схема описывает типы, единицы, даты, ошибки, пагинацию, асинхронные операции и ключи идемпотентности. [FastAPI поддерживает OpenAPI и генерацию клиентского кода на его основе](https://fastapi.tiangolo.com/features/); генерация Android SDK не выполняется на этапе спецификаций.

Внутренний User ID не совпадает с Telegram ID. Привязки внешних идентичностей хранятся отдельно; аутентификация клиента преобразуется в единый серверный principal. Telegram является способом взаимодействия/идентификации, а не обязательным протоколом всех будущих клиентов. Мобильное приложение не будет получать токены бота или доступ к БД. Способ мобильного входа выбирается в будущем Android change; интерфейс доступа не должен требовать браузерной cookie как единственный навсегда допустимый механизм.

Совместимые добавления полей не должны ломать клиентов; несовместимые изменения оформляются новой версией и планом миграции. Мобильный клиент может обновляться позже backend, поэтому нельзя менять значение существующего поля молча. Доступ к текущему пользователю и ресурсу проверяется одинаково для всех клиентов.

Изменяющие запросы получают ключ идемпотентности в контексте субъекта и операции. Повтор с тем же ключом и теми же входными данными возвращает тот же результат; повтор с отличающимися данными отвергается. Конфликтующие изменения подключения защищаются версией записи либо транзакционной блокировкой.

### 4. Состояния подключения и операции различаются

| Текущее состояние | Событие | Результат |
| --- | --- | --- |
| Нет | Создание | pending |
| pending/error | Проверка успешна | active |
| pending | Проверка не прошла или истёк срок | error |
| active | Подтверждён отзыв доступа провайдером | error |
| pending/active/error | Отключение | disabled |
| disabled | Явное повторное включение с проверкой | pending, затем active/error |

Worker повторно проверяет состояние и актуальную версию секрета перед отправкой. Отключение атомарно запрещает новые отправки; границей уже начатой операции считается выдача права отправки worker под согласованной блокировкой. Операцию, начатую до этой границы, нельзя гарантированно отозвать у внешнего сервиса; UI сообщает это ограничение.

Для операций используются состояния queued, running, succeeded, failed, cancelled, unknown. Ошибка отдельной отправки не обязательно означает неисправное подключение.

### 5. Повторы и восстановление

Приём события и запись на обработку должны быть согласованы транзакционно либо через outbox. Worker использует ограниченную аренду задачи; после падения задача возвращается на обработку с тем же идентификатором. Завершённый локальный результат защищается идемпотентностью и уникальностью записей.

Это не обещание exactly-once для внешней платформы. Если worker упал после возможной отправки, а провайдер не поддерживает ключ идемпотентности или запрос результата, операция получает unknown и требует решения оператора. Автоматический повтор допустим только при доказуемо безопасном исходе.

Временные сбои повторяются с задержкой, jitter, конечным числом попыток и общим deadline. Ответ rate limit учитывает Retry-After либо эквивалент провайдера. Ошибки доступа и валидации не повторяются автоматически. Численные значения задаются в provider change, а не выбираются одинаковыми для всех платформ.

### 6. Границы безопасности

- До любого обращения к Connection проверяются субъект и разрешение; отсутствующая область доступа не означает глобальный доступ. Реальная схема входа и ролей определяется отдельным change.
- Секреты передаются по TLS и сохраняются через secret reference либо шифрование с отдельным ключом. Нужны ротация, версии и маскирование диагностик. Примеров реальных токенов в документации и тестах не будет.
- Предлагается frontend и API на одном origin; при раздельных origin нужен явный allowlist CORS. Cookie-сессии, если будут выбраны, потребуют HttpOnly/Secure/SameSite и CSRF-защиты; сам вариант аутентификации пока не выбран.
- Для webhook — отдельная проверка доверия провайдера, размер и частота запросов, дедупликация и проверка timestamp, когда он поддерживается. Пользовательская аутентификация не заменяет проверку webhook.
- Исходящие адреса задаёт доверенный адаптер. Редиректы и DNS-разрешение не должны обходить ограничения адресов; TLS-проверка включена.
- Аудит пишется без payload. Недоступность аудита не должна бесследно пропускать изменение: запись изменения и локальной записи аудита согласуется транзакционно, последующая отправка в журнал может быть асинхронной.

### 7. UX/UI

Предложены список подключений, форма добавления/редактирования, сведения о статусе и подтверждение отключения. Это интерфейс оператора интеграций. Обычный пользователь общается с ботом ingredia и не вводит токен собственного бота; его интерфейс описан в `define-fridge-mvp`. Расширенный UI оператора может следовать после продуктовых сценариев.

Форма сохраняет несекретные поля при ошибках, секрет хранится только в краткоживущем состоянии ввода. Сообщение о результате должно быть доступно вспомогательным технологиям. Для асинхронных действий требуется обновление серверного состояния, а не только оптимистичная смена надписи.

Специализированный UX/UI skill в доступном каталоге для этой работы не найден; установка и применение такого skill не заявляются. При следующих UX-задачах нужно проверить актуальную доступность подходящих навыков. В этом пакете зафиксированы проверяемые UX-требования, без скриншотного тестирования.

### 8. QA только через pytest

Все автоматизированные тесты приложения запускаются через `uv run pytest`; HTTP-клиент, fake clock и тестовые адаптеры могут быть вспомогательными библиотеками, но не отдельными тестовыми фреймворками.

| Область | Способ проверки | Ключевые случаи |
| --- | --- | --- |
| Прикладные правила | pytest unit | Переходы состояний, ограничения прав, неверные capabilities |
| HTTP API | pytest с ASGI-клиентом | Схемы ответов, отказ доступа, ошибки, отсутствие секретов |
| Адаптеры | Общие pytest contract-наборы | Подпись, нормализация, лимиты, исключения и таймауты |
| Хранение и worker | pytest integration на PostgreSQL | Конкурентные дубли, атомарность, аренда, падение и повтор; SQLite не заменяет проверку поведения PostgreSQL |
| Безопасность | pytest negative cases | Чужой ID, webhook forgery, SSRF, oversized payload, утечка токена |
| React-интерфейс | Ручная сценарная приёмка | Клавиатура, фокус, ошибки, ширина 320 px, текст 200%, потерянный ответ |

Проверка сборки и типов TypeScript — техническая проверка компиляции, не второй тестовый фреймворк. pytest не доказывает корректность DOM, фокуса или отображения React. Jest/Vitest, браузерные runners и сравнения скриншотов не планируются. Остаточный риск UI-регрессий фиксируется в отчёте приёмки.

Сетевые вызовы реальных провайдеров исключаются из обычного тестового запуска. Отдельный опциональный smoke-сценарий, также через pytest, возможен после выбора платформы и предоставления тестовых учётных данных; ограничения и реальные внешние действия должны быть заранее определены.

### 9. Docker Compose для локального и первого серверного запуска

Пользователь подтвердил Docker для локального запуска и последующего размещения на сервере. Для первой версии предлагается Docker Compose на одном сервере: одинаковые версии образов приложения в локальной и серверной конфигурации, различаются настройки окружения. Состав: FastAPI API, отдельный worker из того же Python-проекта, frontend React/TypeScript и PostgreSQL. Выбранный позднее локальный AI-сервис может стать дополнительным контейнером; внешний AI API остаётся внешним сервисом. Android-клиент не контейнеризуется.

Сборка Python-образа использует зафиксированные зависимости через uv; frontend собирается отдельно. Контейнеры приложения запускаются без root, образы не содержат токенов и production .env. Локальные секреты могут поступать из исключённого из Git файла, серверные — через выбранный механизм секретов. PostgreSQL и worker доступны только во внутренней сети Compose; наружу выводятся лишь необходимые HTTP-точки входа через выбранный TLS-терминатор. Конкретные сервер, домен, TLS-терминатор, версии базовых образов и способ доставки секретов выбираются перед серверной реализацией.

Данные PostgreSQL размещаются в постоянном томе, независимом от жизненного цикла контейнера. Размещение временных фото/голосовых и их очистка определяются отдельно; они не должны по ошибке зависеть от файловой системы контейнера. План развёртывания включает миграции схемы, резервное копирование и проверку восстановления. Healthcheck, порядок запуска и политика перезапуска помогают обнаруживать и восстанавливать сбои, но сами по себе не дают высокой доступности. Для первого релиза критерий — воспроизводимый чистый запуск, сохранение данных при пересоздании контейнеров и документированный путь восстановления.
## Risks / Trade-offs

- Назначение продукта уточнено → общая основа применяется совместно с `define-fridge-mvp`; личный холодильник и оператор интеграций разделяются по правам.
- Неизвестны гарантии провайдера → отдельный adapter change фиксирует дедупликацию, порядок, сроки и неустранимую неопределённость доставки.
- Только pytest без браузерного исполнения → автоматическое покрытие frontend ограничено; нужна ручная UX-приёмка.
- Worker и устойчивое хранение усложняют старт → они нужны для восстановления интеграционных операций; размер сервера и транспорт очереди выбираются по нагрузке.

## Migration Plan

Миграция существующей системы сейчас не требуется. После отдельного запроса на реализацию выполнить фазы из roadmap, подключить тестовую платформу и пройти критерии приёмки перед production. Для первого выпуска заранее описать восстановление хранилища, остановку приёма и worker, обработку незавершённых операций и откат схемы, не предполагая возможность отмены уже отправленных внешних сообщений.

## Blocking decisions before implementation

В product-brief зафиксированы сценарии, Telegram, PostgreSQL, Docker и будущий Android; ВК отложен. Детали входа в веб и привязки Telegram нужны до реализации доступа, конфигурация PostgreSQL и worker — до обработки реальных событий, параметры протокола и хранения — до запуска Telegram. Задачи ниже являются предварительным планом с явными зависимостями; продуктовый порядок фаз задан в актуальном roadmap.
