# ingredia — инструкции проекта

## Текущий этап

Подготовка и уточнение спецификаций. Пользователь разрешил планирование, но явно исключил общую реализацию. Позднее отдельно разрешена узкая настройка Telegram: локальный `.env`, загрузка через Pydantic Settings и соответствующая зависимость. Остальные код приложения, тесты, миграции и инфраструктуру не создавать без отдельного запроса на реализацию. Наличие tasks.md не означает разрешение выполнять его задачи.

## Зафиксированные требования пользователя

- ingredia — виртуальный холодильник: учёт продуктов, рецепты по имеющимся продуктам и личное избранное с сохранением, списком, открытием и удалением.
- В MVP входит веб-админка управления пользователями; минимальный план: список/поиск, карточка аккаунта, блокировка/разблокировка и аудит с серверной проверкой административных прав.
- Единственный канал MVP — Telegram. ВК только предполагается на будущее: использовать паттерн адаптера и независимое прикладное ядро, не планировать реализацию ВК сейчас. Фото для подбора рецепта сверять с холодильником; непонятный продукт уточнять. Покупки добавлять по фото или голосовому сообщению.
- Хранить количество, объём и сроки годности; средние сроки явно помечать как оценки. Использовать исправления конкретного пользователя для последующих предложений.
- В подборе блюд предусмотреть подтверждаемую коррекцию «Закончилось» с отменой и пересчётом, временное «Не использовать сейчас» без изменения запасов и объяснимый приоритет близких подтверждённых сроков при прочих равных.
- Backend: FastAPI; frontend: React + TypeScript.
- Основная БД — PostgreSQL, выбранная по предложению пользователя. Медиа хранить отдельно от реляционных данных.
- Docker нужен для локального запуска и последующего размещения на сервере; для первого развёртывания запланирован Docker Compose.
- Android-приложение планируется в будущем: сохранять общий версионируемый API и идентичность пользователя, независимую от Telegram. Android сейчас не реализовывать.
- Python, окружения и зависимости управляются через uv.
- Единственный тестовый фреймворк и точка входа автоматизированного QA: pytest, запуск через `uv run pytest`.
- Ruff и mypy проверяют Python-код; pre-commit запускает их перед коммитом. Докстринги пишутся в стиле Google.
- Не добавлять Jest, Vitest, Cypress, Playwright или скриншотные/визуальные regression-тесты. Если понадобится браузерный QA, сначала уточнить допустимый подход.
- Проектировать безопасность с начала работы: минимальные привилегии, проверка доступа к объектам, безопасное хранение секретов, проверка входных данных, аудит и ограничение ресурсов.
- При UX/UI-работе использовать доступные релевантные skills; не утверждать, что навык установлен или применён, без проверки. Скриншотное тестирование исключено.
- Подключение ботов проектировать через расширяемые адаптеры с явными возможностями и ограничениями провайдеров.
- Фичи и фазы планировать через OpenSpec.
- В начальных фазах сравнить бесплатные LLM, модели анализа изображений и распознавания речи. Для голоса оценить готовые сервисы и модели, локальный запуск и собственную адаптацию при доказанной необходимости; выбрать способы подключения и устойчивой работы при сбоях, лимитах и недоступности. Конкретные модели пока не выбраны.

## Проектные скиллы

Использовать подходящий скилл из .agents/skills при задачах его области; перед работой читать соответствующий SKILL.md. Скиллы не расширяют разрешение на реализацию: пока допускаются спецификации и явно разрешённые узкие настройки.

- pytest-test-authoring — проектирование тест-кейсов; писать pytest-код только после разрешения реализации.
- qa-verification — проверка изменений и отчёт о фактически запущенных проверках.
- react-ux — UX/UI и доступность React/TypeScript без скриншотного тестирования.
- product-discovery — исследование рынка и обоснованные продуктовые предложения.
- openspec-feature-planning — оформление новых фич и фаз через OpenSpec.
- security-best-practices — применять при явном запросе на безопасность, аудит или secure-by-default код.

Если нужный скилл недоступен, сообщить об этом и продолжить по правилам проекта.

## Работа со спецификациями

Перед изменениями читать `README.md`, `docs/product-brief.md`, `openspec/roadmap.md` и соответствующий change.
Документы писать на русском; служебные заголовки OpenSpec, идентификаторы и SHALL/MUST сохранять на английском.
Каждой новой возможности соответствует `openspec/changes/<change>/specs/<capability>/spec.md` с проверяемыми WHEN/THEN-сценариями.
Архитектурные решения помещать в design.md, проверяемые требования — в spec.md, задачи и критерии завершения — в tasks.md.
Различать требования пользователя, предложенные решения и неизвестные данные. Не придумывать предметную область ingredia по названию.
Не архивировать change и не переносить проектируемое поведение в `openspec/specs/` как реализованное.

## Проверка результатов

На текущем этапе проверять структуру OpenSpec, согласованность документов, ссылки и полноту сценариев. Проверка формата спецификаций не является тестированием приложения.
После разрешения реализации предусматривать в pytest успешные сценарии, ошибки, границы доступа, повторы событий и сбои интеграций.
Не выдавать API-тесты за проверку поведения React в браузере. Ограничения UI-проверки фиксировать явно.
Не записывать реальные токены, пароли, персональные данные и payload production-событий в документацию или фикстуры.
